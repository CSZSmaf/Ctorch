# 架构

Ctorch 以 eager 执行为基础。模型由普通 C++ 控制流组合算子，稳定的计算结构也可显式编译成可复用计划。C17 包装只负责句柄与参数转换，计算仍进入同一引擎。

## 分层

| 路径 | 职责 |
| --- | --- |
| include/dl | 公开 C++ 与 C17 接口 |
| src/core | Storage、Layout、Tensor、类型与随机生成器 |
| src/autograd | 反向 DAG、保存值、显式梯度与贡献累计 |
| src/ops | 算子语义、无图数值调用与一阶 VJP |
| src/kernels | CPU/CUDA 数值计算体 |
| src/backends | 数值分派、设备上下文、BLAS/cuDNN 适配 |
| src/nn、src/optim | 模块、模型层、优化器与训练控制 |
| src/data、src/io | 批次整理、预取、权重与训练状态 |
| src/plan | 算子规格、固定结构调度与工作区 |
| src/api | C ABI、拥有型句柄与异常转换 |
| extensions/npu | 独立 OpenVINO 推理模块 |

## 表示与所有权

`Storage` 管理分配及其设备生命周期。`Layout` 保存 shape、stride 和元素偏移。`Tensor` 持有张量身份，视图可共享 Storage 并采用不同布局；算子用这些元信息描述地址访问，不要求所有输入连续。

CPU 内核以类型化循环和小型 C 数值函数组织。CUDA 上下文拥有计算与复制 stream、库句柄和专用内存池。BLAS 与设备库的格式转换集中在后端，公开 Tensor 头文件不依赖 CUDA 头文件。

CUDA 资源在所属设备上释放。回收入口读取调用线程当前的设备，仅在设备不同的时候切换，结束后恢复原选择。这使普通单卡训练省去重复切换，也能与其他 CUDA 库共用调用线程。

CPU 卷积按行展开窗口，同一行复用有效列范围。Softmax 每行计算一次起始地址，再沿归约轴的步长访问。LayerNorm 和 RMSNorm 对连续张量使用线性下标，对非连续视图使用布局下标，两条路径共用归一化公式。这些内核把布局解析移到外层，减少逐元素的地址计算。

逐元素遍历把坐标进位与内层循环分开，连续和广播步长通过局部模板固定。普通训练的 `MemoryGuard` 与执行计划共用缓冲池；归还凭据由共享所有权持有，最后一个张量或保存值释放后才复用该块。

## 求导与数值计算

公开算子调用共同的无图数值层，并按输入的求导需求记录反向节点。节点保存所需的数据或紧凑统计，反向公式用无图数值运算实现一阶 VJP。

求导节点的释放使用迭代遍历。直接丢弃一个较深的前向图时，独占分支逐项移入工作列表，调用栈深度保持固定。仍由其他结果持有的分支保留完整输入，后续仍可用于反向传播。工作列表复用已有边的存储。

`GradSink` 汇总重复边与共享参数的贡献。独立结果可以转交缓冲所有权；能直接写入最终目标的计算使用覆盖或累计模式。广播梯度归约回原输入形状，局部索引梯度通过目标视图或散射累计。

内部数值层的 `unary_backward_into` 和 `scale_into` 接收连续目标与累计标志，调用方决定结果的存储位置，后端负责数值计算。需要新结果时，分配包装调用同一入口。CUDA 的 `block_reduce` 为归约、Softmax、归一化、损失、梯度处理和大窗口自适应平均池化提供共同的线程块归约，具体公式与线程协作分开维护。

参数与 buffer 由 Module 登记，遍历按身份去重。状态保存用规范名称关联参数和优化器槽，状态加载保留已有张量身份。函数式模块将参数、buffer 和模式作为显式输入输出，复用原有层实现。

## 执行与扩展

固定计划保存算子规格、依赖、别名和状态语义，复用原有数值与求导入口。工作区在明确的生命周期内复用缓冲；输出、保存值和外部别名继续由共享所有权决定存活时间。

自定义 VJP 接口连接外部计算与求导。DLPack 只负责共享数据与生命周期，设备转换、精度转换和跨框架求导由调用方显式组织。NPU 推理保留在独立目标中，不参与 CPU/CUDA 训练分派。

公共实现使用 RAII、普通函数、局部模板及少量虚接口。文件和设备操作通过异常报告失败，C ABI 入口将异常转换为状态码和线程内错误信息。

## 使用方式与实现成本

常用训练由清空梯度、前向计算、反向传播和参数更新组成。固定的层序列使用 `Sequential::append`，包含分支的模型使用普通 `forward` 函数。参数登记负责名称、共享关系和状态遍历，模型代码只描述计算过程。

模板用于数据类型、布局和内层计算规则。张量的形状、设备和求导需求保留在运行时，后端在一次算子入口选择实现。模块和 VJP 的虚调用处理整项操作，逐元素循环直接调用具体计算体。

Ctorch 使用编译库提供实现，应用通过 CMake 目标取得头文件、编译要求和依赖。C++ 接口使用标准容器和共享所有权，动态库与应用需要匹配的编译工具链。C ABI 用句柄和显式释放函数连接其他语言。

## 相关框架的设计

不同框架面向的任务有所不同。下面比较接口组织和实现方式，运行速度需要使用相同负载单独测量。

| 项目 | 主要设计 | Ctorch 的选择 |
| --- | --- | --- |
| [PyTorch C++](https://docs.pytorch.org/cppdocs/frontend.html) | Tensor、Module、优化器、数据加载和序列化组成完整训练接口 | 采用相近的模块组合和训练步骤，保持普通 C++ 控制流 |
| [TensorFlow](https://www.tensorflow.org/guide/intro_to_graphs) | eager 与 `tf.function` 图执行配合，图可用于优化和部署 | eager 作为常用入口，稳定结构显式建立执行计划 |
| [MLX](https://ml-explore.github.io/mlx/build/html/usage/compile.html) | 函数变换、图编译和操作融合，按输入规格复用编译结果 | 显式状态与固定计划复用现有算子，先处理有完整训练收益的局部融合 |
| [Flashlight](https://github.com/flashlight/flashlight/blob/main/flashlight/fl/tensor/README.md) | 小型 Tensor 后端接口支持不同数值实现，模型与应用分层 | CPU/CUDA 共用算子语义和 VJP，设备库集中在后端 |
| [tiny-dnn](https://github.com/tiny-dnn/tiny-dnn) | 头文件接入与简单层组合，主要面向小型 C++ 网络 | 提供短小示例，数值实现放在编译库中，减少应用重复编译 |
| [dlib DNN](https://dlib.net/dnn_introduction_ex.cpp.html) | 模板类型组合网络，trainer 管理训练及恢复，CUDA/cuDNN 加速计算 | 内层计算使用模板，模型结构使用对象和函数，便于运行时组合 |
| [mlpack ANN](https://www.mlpack.org/doc/tutorials/ann.html) | 模型、损失、初始化和优化方法分别组织 | 保持模型与优化器解耦，状态式和函数式更新共用数值算法 |
| [ggml](https://github.com/ggml-org/ggml) | C/C++ 张量、后端缓冲、内存安排及量化计算 | 用工作区复用存储，输出和求导保存值仍有独立生命周期 |

PyTorch 和 TensorFlow 的算子、设备及部署生态更广。TensorFlow 的 Keras 训练接口主要面向 Python，比较 C++ 使用成本时还需要分别考虑其 C++ 接口。ggml 的量化与设备后端适合学习推理实现；训练框架还需要完整的求导、优化器和续训状态。

## 功能范围

| 方面 | 当前能力 | 可继续扩展的部分 |
| --- | --- | --- |
| 模型与训练 | MLP、CNN、循环网络、Transformer、常用损失和优化器 | 更多算子、任务数据管线和长程训练覆盖 |
| 自动求导 | 动态一阶反向、显式梯度、自定义 VJP、激活重算 | 高阶求导、前向模式和自动批量变换 |
| 设备与精度 | CPU FP32/FP64，CUDA FP32 与 FP16/BF16 混合精度 | 多 GPU、稀疏与量化训练；NPU 当前作为独立推理模块 |
| 执行计划 | 固定规格、槽位与存储复用、无用值消除、局部融合 | 更丰富的局部改写和通用代码生成 |
| 数据与恢复 | 批量整理、异步传输、预取、采样及完整训练状态 | 后台 CPU 解码与整理、多进程数据加载 |
| 互操作与部署 | C ABI、DLPack、CMake 安装包、OpenVINO 推理扩展 | ONNX 导出和更多部署平台 |

当前 CUDA 路径允许非确定性归约。随机 key 和生成器状态控制随机采样，逐位复现还取决于算子的归约顺序及设备库选择。

## 增加一个算子

1. 在公开接口和 `src/ops` 中定义形状、类型、别名与求导语义。可由已有算子组合的功能先使用组合实现。
2. 有独立数值算法时，在 `numeric` 层增加入口，通过 Backend 接入 CPU/CUDA。布局推导和数学公式分别维护。
3. VJP 只保存反向所需的数据。可以写入最终梯度目标时，使用现有覆盖与累计接口。
4. 按使用范围增加 C ABI 包装或计划操作。回归程序分别比较前向、梯度、别名和连续训练，并与主体源码分开。

性能优化先测完整训练和数据管线。重复出现的内核或分配开销再提取公共实现。宿主句柄、小向量或引用计数的替换需要对应的分配与耗时证据，避免让底层类型改动影响全部接口。
